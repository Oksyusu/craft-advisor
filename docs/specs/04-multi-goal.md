# 사양서 04: 여러 목표를 하나의 목록으로

> 상태: **초안 (승인 대기)**. 승인 전에는 구현하지 않는다.

## 메타데이터
- 작성일: 2026-11-13
- 출처: `docs/feature-research.md` 4절 (원본: ETT – EMI Tree Tabs)
- 작업량 추정: 중간
- **선행 사양: 03** (목표와 재고를 합칠 때 03의 재료 키를 쓴다)
- 관련: 07(목록 줄 클릭, 어느 목표가 얼마나 원하는지 마우스 올림 표시)
- 배정된 한계: "`/ai`를 여러 번 하면 재고를 각각 계산함"

## 목표
기계 여러 개를 한꺼번에 준비할 때, 목표들을 쌓아 두고 **재고를 한 번만 세는** 합친 부족 목록을 본다.

## 현재 상태 (코드 기준)
- `AdvisorFlow.craft`: 목표 하나, 개수는 `TARGET_AMOUNT = 1` 고정.
- `CraftPlanner.plan(target, amount, inventory)`: 인벤토리 사본(`pool`) 하나로 트리를 푼다. 남은 중간 재료도 `pool`에 다시 넣어 이후 칸이 쓴다. → 여러 목표를 **같은 `pool`로 차례로** 풀면 그대로 확장된다.

## 범위
### 1. 명령
| 명령 | 동작 |
|---|---|
| `/ai add <아이템> [x개수]` | 목표를 찾아 목록에 넣는다. 같은 목표가 이미 있으면 개수를 더한다 |
| `/ai list` | 합친 계산 결과를 채팅(과 손에 든 클립보드)에 보여 준다 |
| `/ai remove <번호>` | `list`에 나온 번호의 목표를 뺀다 |
| `/ai clear` | 목록을 비운다 |

- **개수 표기:** 끝에 `x4`, `×4`, `4개`가 있으면 개수로 읽는다(1~999, 기본 1). 이 파서는 순수 Java로 만들고 테스트한다. Brigadier 정수 인자를 쓰지 않는 이유: 정수 인자와 이어지는 자유 문장 인자가 함께 있으면 해석이 모호해진다.
- **아이템 찾기:** 지금 `/ai`와 같다. 정확한 이름·ID(02의 영어 이름 포함) → 안 되면 AI `pickItem`(키와 동의가 있을 때) → `question`으로 판단되면 "목표 아이템을 찾지 못했어요"를 보여 주고 넣지 않는다. 자유 질문으로 넘기지 않는다.
  - (구현 후 추가) 이름 후보가 없거나 AI가 후보 중에 맞는 것이 없다고 하면, AI가 `search_items` 도구만으로 JEI를 직접 검색한다(최대 4회, 인벤토리·대화 기록 없음). 예: "접착 피스톤" → "sticky piston" 검색 → 끈끈이 피스톤. AI가 답한 uid는 코드가 JEI 아이템 목록에서 확인한 것만 받아들이고, 없으면 "찾지 못했어요".
  - (구현 후 추가) 개수는 이름에 붙여 써도 읽는다: `피스톤x10`, `피스톤10개`, `피스톤×3`. 단 `x` 앞이 영문자·숫자·`_`·`:`이면 이름의 일부로 본다(`pistonx4`, `mod:tier_x2`).
- `add`는 넣은 목표와 현재 목록 개수만 짧게 알린다. 계산, JEI 화면, 클립보드, AI 조언은 하지 않는다.
- 기존 `/ai <질문>` 한 번 계산은 목록과 무관하게 지금처럼 동작한다.

### 2. 계산기 확장 (`CraftPlanner.planAll`)
```java
MultiPlan planAll(List<Goal> goals, Map<IngredientKey, Integer> inventory)
record Goal(IngredientKey item, int amount)
record MultiPlan(List<Goal> goals, List<Step> steps, List<Missing> missing,
                 List<IngredientKey> machines, Map<IngredientKey, Map<Integer, Integer>> missingByGoal, List<Choice> choices)
```
- 목표 순서대로 **하나의 공유 `pool`** 로 푼다. 먼저 넣은 목표가 재고를 먼저 쓴다.
- 각 목표의 깊이 0은 지금처럼 이미 가지고 있어도 만든다.
- 같은 재료의 부족분과 제작 단계는 합친다. `missingByGoal`은 부족 재료마다 "몇 번 목표가 몇 개" 기여했는지 기록한다(07의 마우스 올림 표시용).
- 기존 `plan(target, amount, inventory)`는 `planAll(List.of(new Goal(target, amount)), inventory)`의 결과를 `CraftPlan`으로 돌려주는 얇은 함수로 남긴다. 기존 테스트가 그대로 통과해야 한다.

### 3. `/ai list` 표시
- 채팅: 목표 목록(번호, 이름, 개수) → 필요한 기계 → 합친 부족 재료.
- 클립보드(손에 들고 있을 때): 합친 부족 재료를 **한 묶음의 페이지로** 덧붙인다. 머리 줄은 "목표 N개 합계". 덧붙이기·페이지 나누기·클릭 이벤트 금지 규칙은 지금 `CreateClipboardWriter`와 같다.
- AI 조언은 부르지 않는다(아래 결정 필요 2).
- 계산할 때마다 인벤토리를 새로 읽는다(목표를 넣은 시점의 인벤토리가 아님).

### 4. 목록 보관
- 클라이언트 메모리에만 둔다. 게임을 끄면 사라진다(아래 결정 필요 1).
- 목표 상한 20개.

## 범위에서 빼는 것
- 목표별 이름·색이 있는 단계(phase) 묶음, 탭 화면
- 목표 간 우선순위 바꾸기(순서 바꾸기 명령). 필요하면 `remove` 후 다시 `add`
- 상자 등 인벤토리 밖 재고

## 명령어 예약어
`add`, `list`, `remove`, `clear`는 리터럴 하위 명령이라 이 단어로 시작하는 자유 질문은 하위 명령으로 처리된다. 전체 예약어는 01 참고.

## 완료 기준
- [ ] 1. 단위 테스트: 두 목표가 각각 철 주괴 10개를 원하고 인벤토리에 10개 있으면 합친 부족은 10개다(연구 문서의 ETT 예시).
- [ ] 2. 단위 테스트: 첫 목표에서 남은 중간 재료(출력 개수 2 이상 레시피의 나머지)를 두 번째 목표가 쓴다.
- [ ] 3. 단위 테스트: `missingByGoal`의 합이 부족 개수와 같다.
- [ ] 4. 단위 테스트: 목표 하나짜리 `planAll` 결과가 기존 `plan` 결과와 같다(기존 테스트 전부 통과).
- [ ] 5. 단위 테스트(개수 파서): `기계식 피스톤 x4`, `기계식 피스톤 4개`, `x0`·`x1000` 거부, 개수 없음은 1.
- [ ] 6. 게임 확인: `/ai add 기계식 피스톤 x2`, `/ai add 톱`, `/ai list` → 합친 목록이 나오고, 같은 재료가 한 줄로 합쳐진다. 클립보드를 들고 있으면 페이지가 덧붙는다.
- [ ] 7. 게임 확인: `/ai remove 1`, `/ai clear` 후 `/ai list` → 각각 반영된다.

## 결정 필요 (추천안 먼저)
1. **목록 보관:** 메모리만 추천(가장 단순). 파일로 남기려면 서버·월드별로 나눠야 해서 서버 주소를 로컬에 저장하게 된다.
2. **`/ai list`의 AI 조언:** 부르지 않음 추천(목록을 여러 번 볼 때 비용). 원하면 `/ai list advise`처럼 명시적으로 부르는 형태를 추가한다.
3. **클립보드 페이지 구성:** 합친 목록 한 묶음 추천. 연구 문서의 "목표별 = 페이지" 방식은 공유 재고에서 목표별 부족분이 먼저 넣은 순서에 따라 달라져 혼란스러울 수 있다.
